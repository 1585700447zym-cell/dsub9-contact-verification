## 故障证据与原因

原 worker 在完成物理运行和原始落盘后，调用 `assess_raw`，报 `ValueError: reward.progress differs/nonfinite`，见 [原日志](run/P01_zero.log)。外层确认进程退出，按一次性规则关闭余量，原状态为 `CLOSED_SUPERVISOR_ERROR`。该状态不能据错误文字直接解释为物理数值不稳定。

只读诊断发现审核函数 `same` 对数字采用精确 Python 类型判断：其数字分支只接收 `type(value) in (int, float)`；其他分支又要求左右类型完全相同。生产奖励路径涉及 NumPy 初始位置标量，真实命令重算也生成 NumPy 标量。同一个有限数值在 `float` 与 `numpy.float64` 之间，两个比较方向都会被拒绝。

证据链见 [诊断程序](diagnose_audit.py) 和 [机器诊断](audit_diagnosis.json)：

1. 原始记录 3,045 周期按固定生产 `EpisodeReward` 单独重算，数值不一致 **0**。
2. 对同一 gzip 档案运行未修改的封存审核器，可复现另一个同源类型错误：第 1 周期的 `action log.unfiltered_stage_limited_total`。左右显示值相同，实际类型为 NumPy 标量和 JSON 解码后的普通数值。它先于奖励比较触发，解释了落盘后报错位置不同。
3. 三个“同值、有限、类型不同”反例均被原比较器拒绝，其中包含真实首周期奖励进度值。
4. 仅在诊断进程中把 NumPy 标量还原为其 Python 标量，保持原容差和全部规则，同一档案的命令、奖励、3,046 个 137 维观测、守卫、几何及停止审核通过。真实数值差异、NaN、两个方向的布尔/数值混用共 4 个反例仍被拒绝。

这是上一阶段审核器的实现遗漏；此前纯夹具检查没有覆盖真实 NumPy 标量与序列化数据之间的类型差异。**封存审核器未修改，原运行失败状态未改成通过。** 本轮只完成根因与最小修改的离线验证，尚未交付绑定到新候选的正式修复。
