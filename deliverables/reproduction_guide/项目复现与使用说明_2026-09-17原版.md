# D-sub9 项目复现与使用说明

更新：2026-09-17。适用对象：希望找到模型、阅读报告、查看动画，并在本机重新运行实验的项目使用者。

**建议顺序：先读第 1—3 节，查看已有成果；再按第 4 节重跑一个代表工况；最后决定是否跑完整矩阵。** 全部报告入口见 [报告总索引](报告总索引.md)。

## 1. 当前做到什么，动画为什么只插入一小段

本项目已完成原始几何与接触诊断，并建立简化的笛卡尔动力学执行器和固定导纳 B1。当前还没有完整 CR5、真实夹爪柔性、实物力传感器或训练好的强化学习策略。

当前真实轨迹动画选用的是预先确定的联合偏差 A ×0.75：X 偏差 +45 μm、Y 偏差 −30 μm、roll +1.125°、pitch −1.125°。

| 项目 | 零导纳反馈参考 | B1 固定导纳 |
|---|---:|---:|
| 最终实际 Z 推进量 | 0.156673 mm | 0.246839 mm |
| 撤销推进的仿真时刻 | 3.9 s | 6.0 s |
| 回合结束时刻 | 4.9 s | 7.0 s |
| 终止原因 | 推进停滞 `NO_PROGRESS` | 到达时限 `TIME_LIMIT` |
| 完成插入 | 否 | 否 |

名义目标推进量是 4 mm。这个工况中 B1 的推进仅约为目标的 6%，所以动画显示的确实只是局部推进。回放包含本次记录的整个过程；零反馈回合先结束，其后明确标记“保持末帧”。仿真时间与 GIF 播放时长不同，以画面中的记录时间为准。

这里的“推进量”是公头原点沿世界 Z 轴的位移，不是带倾角时每一根针的实际插入长度，也不是“接触穿透量”。接触穿透是碰撞求解器报告的局部重叠距离，不能和 4 mm 装配行程混为一谈。

该固定参数下，B1 可以减小部分姿态误差、改善推进，但仍没有解除所有受阻。仅延长动画或仿真时间不能保证成功，是否增加时间、改变参数或加入搜索都应作为另一项有记录的试验。下一步拟用受限搜索与恢复策略 B2，针对这些失败工况作对照。

全部 7 个固定工况、14 个回合中，两种方法都只有同轴无接触工况满足几何完成判据。无接触完成证明自由推进流程可用，不能证明导纳纠偏有效。这组小样本不是总体成功率试验。

旧中文包中的动画是按规定姿态推进的准静态展示，可能看起来插得更深。它不受同一动力学控制过程约束，不能用来证明旧控制器比新控制器好。

## 2. 模型在哪里，原解析 SDF 去哪里了

当前工作目录不是外层 `first_stage_sim`，而是：

```text
D:\dsub9项目计划\first_stage_sim\.worktrees\dsub9-v1-contact-validation
```

以下相对路径都相对于这个目录。

| 层次 | 文件或目录 | 用途及当前状态 |
|---|---|---|
| 原 CAD | `DSub9_Deliverables_V4/` 中的 `.SLDPRT`、`.step` | 保留 SolidWorks 原始形状来源 |
| 视觉网格 | `assets/visual/dsub9_male_visual_centered.stl`、`dsub9_female_visual_centered.stl` | 仿真画面中的外观，仍使用原导出及对齐资产 |
| 原解析 SDF 场景 | `models/dsub9_pair.xml` | 原阶段称“正式模型”的 SDF 版本，保留 |
| SDF 插件 | `plugins/dsub9_hole_sdf/hole_sdf.cc`、`hole_sdf.h`、`register.cc` | 有符号距离场及梯度的解析实现，保留 |
| SDF Python 参考 | `tools/sdf/hole_reference.py` | 解析距离核对，保留；也用于独立几何分析 |
| 本机 SDF 编译库 | `build/dsub9_hole_sdf/Release/dsub9_hole_sdf.dll` | 原场景加载需要，属于本地构建产物 |
| 已导出的 128 段模型 | `deliverables/contact_coverage_repair/dsub9_convex128_contact_dev_v1.xml` | 接触覆盖诊断阶段的独立开发模型 |
| 当前 256 段/MPR 模型 | `deliverables/model_exports_256/dsub9_convex256_b1_mpr.xml` | 本次新增的可查找、可加载导出副本 |
| 256 段生成器 | `tools/model/contact_development.py` | B1 此前直接调用它在内存中生成 256 段模型 |

**视觉形状与碰撞表示是两层。** SolidWorks 导出的外观仍保留；当前替换的是孔的碰撞表示。每个孔的入口和主孔各分成 256 个凸块，9 个孔共有 4608 个孔壁碰撞 geom。针仍为圆柱碰撞体，D 形壳碰撞结构沿用之前的模型。

原 SDF 对阶梯孔实体给出解析距离，并不意味着当前碰撞搜索配置一定能找到所有接触。之前的独立几何核对发现，部分存在重叠的姿态漏生成了针孔接触。因此采用凸分块替代路径继续开发，原 SDF 路径没有删除，也不能宣称已经修复。

256 段主孔最大径向放大量约 0.043300 μm、入口约 0.050830 μm，属于近似圆孔。它保留原 0.25 mm 深阶梯入口，没有新增倒角。此前部分动态工况对 128/256 分辨率仍敏感，所以不能把 256 段当作物理真值。

打开当前模型：

```powershell
Set-Location -LiteralPath 'D:\dsub9项目计划\first_stage_sim\.worktrees\dsub9-v1-contact-validation'
& 'D:\KEYANRUJIAN\python.exe' -X utf8 -B -m mujoco.viewer --mjcf 'deliverables/model_exports_256/dsub9_convex256_b1_mpr.xml'
```

此命令打开查看器。关闭窗口后命令行返回。XML 依赖原目录中的网格和 include 文件，不能只复制一个 XML 到其他位置。当前本机 MuJoCo 对中文绝对 XML 路径出现过读取失败，应保持以上“进入项目目录 + 相对英文路径”的写法。

XML 只提供场景与求解设置；B1 控制、驱动、保护和工况初始化在 Python 中。打开 XML 不等于启动 B1 插入。原 SDF 场景可以用现有入口查看：

```powershell
& 'D:\KEYANRUJIAN\python.exe' -X utf8 -B -m tools.visualization.launch_viewer --mode sdf
```

只核对原 SDF 能否加载、不打开窗口：

```powershell
& 'D:\KEYANRUJIAN\python.exe' -X utf8 -B -m tools.visualization.launch_viewer --mode sdf --check-only
```

## 4. 真正重跑一个代表工况：推荐的首次复现

下面流程从已提交的 B1 版本 `1645282` 导出独立副本，再重新计算。它不会覆盖当前正式成果。首次运行时不需要重建 SolidWorks 模型，不需要训练 GPU，不需要连接机械臂。

### 4.1 本机环境检查

打开 PowerShell，执行：

```powershell
$taskProject = 'D:\dsub9项目计划\first_stage_sim\.worktrees\dsub9-v1-contact-validation'
$taskPython = 'D:\KEYANRUJIAN\python.exe'
Set-Location -LiteralPath $taskProject
git rev-parse --short HEAD
& $taskPython -X utf8 -B -c "import sys,mujoco,numpy,matplotlib,PIL,pytest; print(sys.version); print('MuJoCo',mujoco.__version__,'NumPy',numpy.__version__,'Matplotlib',matplotlib.__version__,'Pillow',PIL.__version__,'pytest',pytest.__version__)"
Test-Path -LiteralPath 'build/dsub9_hole_sdf/Release/dsub9_hole_sdf.dll'
```

2026-09-17 本机核对环境：Windows x64、Python 3.13.5、MuJoCo 3.9.0、NumPy 2.1.3、Matplotlib 3.10.0、Pillow 12.2.0、pytest 8.3.4。最后一行应输出 `True`。后续文档提交可能改变 HEAD，但下面显式选用的实验版本仍为 `1645282`。

本指南以本机保存的版本为准。本轮没有推送或合并到 GitHub，不要假定先前的 V1 网页链接已经包含 B1 和这份新说明。若在别处执行 `git archive ... 1645282` 提示版本不存在，先确认该环境是否取得了这个提交。

当前机器已经装好依赖，不需要为了复现重新安装或升级。不同 MuJoCo 版本可能改变接触与数值结果。

### 4.2 建立不会覆盖原成果的独立副本

在同一个 PowerShell 窗口继续执行，保留上面的两个变量：

```powershell
$taskStamp = Get-Date -Format 'yyyyMMdd_HHmmss'
$taskReplica = Join-Path $taskProject ('tmp\b1_reproduce_' + $taskStamp)
$taskZip = Join-Path $taskProject ('tmp\b1_baseline_' + $taskStamp + '.zip')
New-Item -ItemType Directory -Path (Join-Path $taskProject 'tmp') -Force | Out-Null
if (Test-Path -LiteralPath $taskReplica) { throw '复现目录已存在，请更换目录名。' }
git archive --format=zip --output=$taskZip 1645282
if ($LASTEXITCODE -ne 0) { throw '版本导出失败，请检查当前目录和 Git。' }
Expand-Archive -LiteralPath $taskZip -DestinationPath $taskReplica
$taskDllDir = Join-Path $taskReplica 'build\dsub9_hole_sdf\Release'
New-Item -ItemType Directory -Path $taskDllDir -Force | Out-Null
Copy-Item -LiteralPath (Join-Path $taskProject 'build\dsub9_hole_sdf\Release\dsub9_hole_sdf.dll') -Destination $taskDllDir
Set-Location -LiteralPath $taskReplica
Write-Output ('本次复现目录：' + $taskReplica)
```

归档约 166 MiB 的未压缩文件，包含实验记录，实际占用和解压时间随系统而变。副本不带 Git 元数据，可以直接运行。不要在这个副本中使用 `git status` 判断它的版本，以导出的固定提交为准。

特别说明：SDF DLL 是 `build` 下的本机构建产物，不包含在 Git 归档中，所以需要单独复制。虽然 B1 不调用 SDF 进行孔碰撞，当前严格的历史输入指纹检查仍包含这个 DLL。不保留它会在开始前检查失败，这不表示 B1 又切回了 SDF。

### 4.3 重新计算这个工况的两次回合

```powershell
& $taskPython -X utf8 -B -m tools.validation.run_b1_baseline --case combined_a_scale_0.75
if ($LASTEXITCODE -ne 0) { throw '仿真没有正常完成，请保留错误信息。' }
```

此命令没有 `--resume`，会实际执行动力学积分。先运行零反馈参考，再运行 B1。计算期间每完成一个回合打印一行摘要，不会自动弹出动画。GPU 利用率低不表示没有运行：本轮是 MuJoCo 数值控制仿真，不是神经网络训练。

初次复现预计数分钟，取决于 CPU、后台任务与环境；原基线这两个回合共约 123 s。不要用回合耗时是否完全一致判断复现成败。

新结果位于 `$taskReplica` 下：

```text
deliverables/b1_fixed_admittance/runs/combined_a_scale_0.75_reference.json
deliverables/b1_fixed_admittance/runs/combined_a_scale_0.75_b1.json
deliverables/b1_fixed_admittance/pilot_index.json
```

`--case` 运行只更新这个工况的两个回合和单工况索引 `pilot_index.json`，不会重写全矩阵 `results_index.json`。此时另外 6 个工况仍是归档中的原始结果，不能称为你已重跑了全部 14 个回合。

相同本机环境的实际重跑核对见 [复现实测记录](deliverables/reproduction_guide/复现实测核对.json)。计时字段可以不同；如果终止原因、推进量或载荷明显不同，先核对版本、Python 路径、MuJoCo 版本和输入指纹，不要先改控制参数去凑结果。

## 5. 完整重跑 B1 的全部 7 个工况

在第 4 节建立的独立副本中执行：

```powershell
& $taskPython -X utf8 -B -m tools.validation.run_b1_baseline
if ($LASTEXITCODE -ne 0) { throw '完整矩阵未完成，请保留错误信息。' }
& $taskPython -X utf8 -B -m tools.reporting.report_b1
& $taskPython -X utf8 -B -m tools.visualization.replay_b1
```

不加 `--case`，不加 `--resume`，会重新计算 14 个回合并更新 `results_index.json`。完整原基线记录的回合耗时合计约 803 s（13.4 min），不含准备和绘图时间；本机负载不同可以更慢。

预期结果为：两种方法各有 1 个同轴无接触几何完成，其余接触工况均未完成插入。不要期待重跑后自动变成全部成功。

运行相关测试：

```powershell
& $taskPython -X utf8 -B -m pytest tests/control tests/dynamics tests/contact/test_contact_development.py tests/contact/test_applicability.py -q
```

原基线该命令为 96 项通过。这证明这些实现检查通过，不代表所有装配工况成功，也不替代数值一致性和实物标定。

```powershell
Set-Location -LiteralPath $taskProject
```

## 6. 三种容易混淆的运行方式

| 方式 | 实际做了什么 | 是否重新积分 |
|---|---|---|
| 打开 PNG、GIF、PPT、报告 | 查看已经生成的成果 | 否 |
| `report_b1` / `replay_b1` | 读取 JSON 重绘图表或回放已保存位姿 | 否 |
| `run_b1_baseline --resume` | 对已有、指纹一致的文件直接复用；缺失回合才计算 | 不一定；文件齐全时否 |
| `run_b1_baseline`，不加 resume | 重新计算选定工况或全部工况，写入当前项目目录 | 是 |

因此，正式目录中直接运行不带 `--resume` 的实验会覆盖相应回合。建议始终用第 4 节的独立副本进行探索，保留原基线。

## 7. 其他历史阶段如何使用

这些是可选的历史研究步骤，不需要每次运行 B1 都从 SolidWorks 开始做一遍。以下表格列出入口，本次没有重新执行全部历史诊断。

第 4 节的无 Git 元数据归档副本专门用于 B1。部分历史诊断会读取 Git 提交号，因此应在另建的、保留 Git 元数据并锁定相应历史版本的独立工作树中运行，不能直接沿用无 Git 归档来证明历史版本来源。以下计算命令会重写各阶段结果，不要在正式目录中随意依次执行。

| 历史阶段 | 入口 | 结果位置 |
|---|---|---|
| V1 已有成果只读核对 | `python -m tools.validation.run_v1_contact_validation --check-only` | 控制台显示核对摘要 |
| V1 规定姿态接触验证重跑 | `python -m tools.validation.run_v1_contact_validation` | `reports/` 与早期中文图表目录 |
| SDF 适用性诊断 | `python -m tools.validation.diagnose_v1_applicability` | `deliverables/v1_applicability/` |
| 凸分块覆盖诊断 | `python -m tools.validation.repair_contact_coverage`；再运行 `python -m tools.reporting.report_contact_coverage_repair` | `deliverables/contact_coverage_repair/` |
| 动态执行器矩阵 | `python -m tools.validation.validate_dynamic_actuator`；再运行 `python -m tools.reporting.report_dynamic_actuator` | `deliverables/dynamic_actuator_v1/` |

表中 `python` 应替换为 `& $taskPython -X utf8 -B`，并在正确目录执行。历史报告要连同当时的源文件指纹理解；重建 DLL、改动旧报告或输入文件后，严格核对可能拒绝混用旧结果，应另立实验版本。若要复现某个历史阶段的原始数值，应再核对该阶段记录的版本与配置，而不把最新分支上的任意修改混进去。

月报可直接在 PowerPoint 编辑，不需要重跑科学实验。逐页 PNG 是定稿时的快照；如果修改 PPT，PNG 不会自动更新。程序化重建月报使用已保存的 `tools/reporting/build_monthly_progress.mjs` 和本机演示文稿运行库，属于可选制作流程，不是 B1 仿真依赖。

第 4 节锁定的 `1645282` 是实验基线，早于本次说明和 256 段 XML 导出文件。副本里没有新说明或新导出文件是正常现象，B1 仍通过原生成器在内存中构建同一 256 段模型。查看新导出模型请回到正式工作目录。

## 8. 常见问题

| 现象 | 原因与处理 |
|---|---|
| `No module named tools` | 通常进入了外层目录。按第 4 节先进入真正的工作目录或独立副本 |
| `No module named mujoco` | 用了不同 Python。先用 `D:\KEYANRUJIAN\python.exe` 核对 |
| 缺少 `dsub9_hole_sdf.dll` | Git 不包含本地 build 文件。当前机器按第 4 节复制已验证 DLL；新机器需准备兼容构建环境或迁移该构建产物 |
| `Stale B1 checkpoint` 或 `Stale ... evidence` | 源码或历史输入指纹变化。保留错误并检查差异，不删除校验、不把新旧数据混合 |
| 中文绝对路径下 XML/DLL 打不开 | 使用已核对的相对英文路径，从项目根目录启动 |
| 没有仿真窗口、只有一行行摘要 | 批量实验默认无窗口，完成后用回放脚本生成 GIF |
| GIF 看起来几乎不动 | 该实验实际推进小，局部视图保持真实尺寸比例，没有人为放大位移 |
| 重新运行后 JSON 哈希不同 | 计时字段可能不同。科学结果应比较状态轨迹、峰值、事件与终止原因，同时核对输入哈希 |
| 老报告说“尚无控制器” | 那是几何或 V1 阶段的历史状态。当前 B1 进度以本说明与 B1 报告为准 |
| 看不到某些文件夹 | `.worktrees` 是实际成果所在目录的一部分。可把完整路径粘贴到资源管理器地址栏 |

## 9. 更换机器与归档

本说明的实际复现核对针对当前 Windows 机器。换机器时至少保留原 CAD/网格、模型 include、控制代码、固定版本、完整输入、历史记录与必要的 DLL。普通 Git 克隆不能代替本地 build 产物，运行截图也不能代替原始轨迹。

建议先复制完整可运行工程到新机器的英文目录，在单独环境中匹配本说明列出的 Python 与核心库版本。SDF 重新编译说明见 [插件 README](plugins/dsub9_hole_sdf/README.md)。重新编译后的 DLL 可能与旧二进制指纹不同，这时属于新环境复验，不能假称旧输入完全一致。

本轮工作不需要重新导出 SolidWorks 模型、实际夹持位置、完整 CR5 或 GPU 训练。实机对应与迁移前仍需补齐夹持和工具变换、负载惯量、传感器与接触参数标定。
